## 1. Матрица требований к серверной валидации

| Описание инцидента | Тип требуемой серверной проверки | Конкретное правило |
| :--- | :--- | :--- |
| **1. Бронь переговорной комнаты** с датой начала 2026-12-01 и датой окончания 2026-11-01. | Проверка диапазона/формата (Range/Format validation) и бизнес-логики (Business logic validation). | start_date и end_date соответствуют формату ISO 8601; start_date >= current_date; строго выполняется end_date > start_date. |
| **2. Заявка на выдачу -50 ноутбуков** пользователем с возрастом -5 лет. | Проверка типа данных (Type checking) и диапазона/формата (Range/Format validation). | Поля laptop_count и user_age имеют строгий тип integer; 1 <= laptop_count <= 100; 18 <= user_age <= 100. |
| **3. Самостоятельное присвоение роли super_admin** в JSON-запросе. | Проверка авторизации/ролей (Authorization). | Поле role игнорируется во входной DTO-модели; смена роли разрешена только пользователю с действующей ролью super_admin через отдельный админ-эндпоинт. |

## 3. Архитектурное решение методом WSM (Weighted Sum Model)

### 3.1. Обоснование весов критериев
* **Надежность (0.35):** Максимальный вес, так как после критического инцидента главный приоритет — гарантированная целостность данных.
* **Гибкость изменения правил (0.30):** Высокий вес, так как бизнес-правила бронирования меняются часто и требуют быстрого обновления в коде без миграций БД или перенастройки шлюза.
* **TCO — сложность поддержки и обучения (0.20):** Средний вес, важно поддерживать правила силами текущей команды в едином стеке.
* **Производительность (0.15):** Базовый вес, так как корпоративная система не является высоконагруженной (миллисекунды менее критичны, чем надежность).

### 3.2. Матрица решений

| Критерий оценки | Вес (Wj) | 1. API Gateway (Балл / Взвеш.) | 2. Application Layer (Балл / Взвеш.) | 3. Database Constraints (Балл / Взвеш.) |
| :--- | :---: | :---: | :---: | :---: |
| Надежность | 0.35 | 2 / 0.70 | 4 / 1.40 | 5 / 1.75 |
| Гибкость изменения правил | 0.30 | 3 / 0.90 | 5 / 1.50 | 2 / 0.60 |
| TCO (поддержка и обучение) | 0.20 | 3 / 0.60 | 5 / 1.00 | 3 / 0.60 |
| Производительность | 0.15 | 5 / 0.75 | 4 / 0.60 | 3 / 0.45 |
| **ИТОГОВЫЙ БАЛЛ (Si)** | **1.00** | **2.95** | **4.50** | **3.40** |

### 3.3. Расчет и вывод
* **API Gateway:** 0.35*2 + 0.30*3 + 0.20*3 + 0.15*5 = **2.95**
* **Application Layer:** 0.35*4 + 0.30*5 + 0.20*5 + 0.15*4 = **4.50**
* **Database Constraints:** 0.35*5 + 0.30*2 + 0.20*3 + 0.15*3 = **3.40**

**Вывод:** Оптимальным выбором является **Application Layer (4.50 балла)**. Вся бизнес-валидация, проверка ролей и санитизация должны реализовываться в коде микросервиса. Дополнительно рекомендуется дублировать базовые критические правила на уровне СУБД (Database Constraints) в качестве страховочного слоя защиты.

## 4. Обновленные пункты Definition of Done (DoD)

1. **Автоматизация (CI/CD Quality Gate):** Для каждого нового или измененного API-эндпоинта написаны негативные интеграционные автотесты, имитирующие отправку некорректных данных в обход фронтенда (отрицательные значения, обратный порядок дат, XSS-нагрузки и подмена роли super_admin), и автоматический CI-пайплайн успешно проходит эти тесты перед релизом.
2. **Процесс ревью (Code Review Gate):** Каждый Pull Request с новым API-эндпоинтом проверен минимум одним рецензентом с обязательным ручным или автоматическим заполнением целевого чек-листа валидации и безопасности (все пункты должны иметь статус «Да» или «Неприменимо»).
